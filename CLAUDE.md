# TxLens — project instructions for Claude Code

## What this project is
TxLens is a multi-tenant SaaS clinical data and AI platform for organ transplant programs.
It turns messy transplant patient data (clinical notes, lab feeds, scanned biopsy/pathology PDFs)
into standardized OMOP CDM v5.4 data, monitors patients on a post-transplant surveillance schedule,
gives researchers a cohort and survival-analysis workbench, and offers an AI copilot that answers
questions over patient data (guarded text-to-SQL) and transplant literature (cited RAG).

It is a personal portfolio project. It is inspired by public information about precision-medicine
transplant diagnostics companies, but it is NOT affiliated with any company.

## Hard rules
- **Synthetic data only.** Never use, download or request real patient data. All patients, notes,
  labs and PDFs are generated by our own generator in `data_generator/`.
- **No real company or product names in our own words**: code, UI text, docs, generated
  data, reports and the copilot's own answers. The exact list of names to avoid is in
  `CLAUDE.local.md` (git-ignored); the copilot holds only salted hashes of them. Use generic
  terms: "dd-cfDNA assay", "a commercial dd-cfDNA assay", "tumor DNA marker".
  Exception: third-party sources are kept verbatim. Downloaded abstracts (out of git) and the
  quotes and titles of cited abstracts, shown with their PMID, may contain such names.
- **Secrets** live only in `.env` (git-ignored). Provide `.env.example` with placeholder values.
  Never print, log or commit API keys.
- **The LLM never makes clinical decisions.** It extracts and summarizes. Rules, thresholds and
  statistics are deterministic Python code. Every AI output keeps a link to its source (document,
  page, sentence) and low-confidence results go to the human review queue.
- **Researcher role sees de-identified data only** (no names, MRNs, exact birth dates; dates shifted).
- Every write and every PHI-view is recorded in the `audit_log` table.

## Tech stack (do not swap without asking)
- Frontend: Next.js (App Router) + React + TypeScript, Tailwind CSS, shadcn/ui, TanStack Query,
  TanStack Table, Plotly.js. Package manager: pnpm. Tests: Vitest + Playwright.
- Backend: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 + Alembic. Package manager: uv.
  Lint/format: ruff. Types: mypy. Tests: pytest.
- Database: PostgreSQL 16 with pgvector. Multi-tenancy enforced with Postgres Row-Level Security
  keyed on `tenant_id` (each tenant = one transplant center).
- Workflows: Temporal (Python SDK) for document processing and other multi-step jobs,
  including human-review wait steps. No Celery/Redis.
- Data platform: PySpark + Delta Lake, medallion layout (bronze -> silver -> gold).
  Gold = OMOP CDM v5.4 tables. Pipelines must run locally AND as Databricks Free Edition jobs
  (Python only on Databricks; no R there). Data quality checks with Pandera.
- AI: LiteLLM as the single LLM interface (default OpenAI; optional local Llama 3.1 8B via Ollama),
  Instructor for schema-validated extraction, LangGraph for the copilot agent, sqlglot to validate
  generated SQL (read-only, allow-listed tables, row limits), medspaCy for clinical NLP/negation,
  Docling + Tesseract for OCR/layout, Langfuse for LLM tracing, RAGAS + custom metrics for evals.
- Stats/ML: pandas, statsmodels, lifelines, scikit-learn, MLflow.
- Retrieval is behind a `VectorStore` interface so pgvector can later be swapped for
  Milvus or Databricks Vector Search.
- Dev/ops: Docker Compose for local stack, GitHub Actions CI, target deploy Azure Container Apps.

## Domain facts used in the app (keep consistent)
- Organs: kidney (primary), heart (secondary).
- dd-cfDNA surveillance schedule: months 1, 2, 3, 4, 6, 9, 12 post-transplant, then quarterly.
- dd-cfDNA thresholds (configurable): >=0.5% possible graft injury, >=1.0% high risk of rejection.
- Other key labs: creatinine, eGFR, tacrolimus trough, donor-specific antibodies (DSA).
- Biopsy outcomes: no rejection, borderline, TCMR, ABMR, mixed.
- Vocabularies: SNOMED CT (conditions), RxNorm (drugs), LOINC (labs). Unmapped -> concept_id 0,
  keep source_value, send to review.
- Surveillance engine is disease-agnostic: marker, thresholds and schedule come from a config
  (second config = oncology tumor-DNA marker monitoring).

## How to work
- Before a big change, show a short plan and wait for approval.
- Build in small steps. After each step: run the tests/linters, fix failures, then summarize.
- Write tests for every module (unit tests, plus integration tests for DB/RLS and pipelines).
- Keep functions small, typed and documented. No dead code.
- After each phase, update `docs/LEARNING.md` with: what was built, why each tool was chosen,
  the trade-offs, and 3-5 likely interview questions with short plain-English answers.
  Write it in simple English for the project owner.
- Record important decisions as short ADRs in `docs/adr/` (context, decision, alternatives, consequences).
- Every metric in the README must come from a script in `evals/` that anyone can re-run.
- Commit after each working step with a clear message.
